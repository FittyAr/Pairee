# Pairee Plugin Registry — Specification

> **Status: Partially implemented. Sections 5 and 6 (CLI, download, verification and signatures) describe the current behaviour; the versioned layout of section 2 is planned.**

---

## 1. Overview

The Pairee Plugin Registry is a community-curated catalog of Lua plugins distributed through a dedicated, standalone Git branch (`plugin-registry`) in the main `FittyAr/Pairee` repository. It provides:

- A versioned, directory-based history of every published plugin release.
- Individual file-by-file SHA-256 integrity verification.
- A structured Pull Request workflow for community submissions.
- A `pairee plugin` CLI for search, list, install, update, check-updates, pin, and removal operations.
- Dynamic keybinding resolver merging, mapping keys defined in plugin manifests directly at load time.
- A secure Developer Mode with format, validate, hash-generation commands, and automated Git branch/PR UI.

---

## 2. Registry Branch Layout

The `plugin-registry` branch is a **standalone orphan branch** (no shared history with `main`). It holds only registry catalog indices and raw plugin directories:

```text
plugin-registry/
├── registry/
│   ├── index.toml                      # Master catalog (auto-generated by CI)
│   ├── blocklist.toml                  # Plugins that may not be installed
│   └── plugins/
│       └── <shard>/                    # First letter of the author, lowercased ('_' if not a-z)
│           └── <author>/               # Manifest `author`, e.g. contributor-handle
│               └── <name>/             # Manifest `name`, e.g. git (latest version only)
│                   ├── manifest.toml   # Registry copy, with the [files] hashes appended
│                   ├── main.lua
│                   ├── utils.lua
│                   ├── sha256.sum      # Checksums of the plugin files
│                   ├── help/
│                   │   ├── en.md       # Default help documentation
│                   │   └── es.md       # Localized help in Spanish
│                   └── lang/
│                       ├── en.toml
│                       └── es.toml
└── CONTRIBUTING.md                     # How to submit a new plugin
```

`<name>` and `<author>` are the manifest `name` and `author`, both
`[A-Za-z0-9_-]` only (the installer refuses anything else) and without a
`.pairee` suffix: Pairee installs the plugin as `<name>.pairee/`. The folder
holds the latest version; older versions stay in the branch history.

**Branch rules:**
- The branch is protected; only CI and maintainers may push to it.
- Versions are **never deleted** — the registry is append-only.
- Developers submit plugins via Pull Requests containing their plugin folder and the `index.toml` entry.

## 3. Schema Definitions

### 3.1 `registry/index.toml`

The index file acts as the master catalog holding metadata for plugin discovery. It does NOT contain file mappings or hashes to minimize size.

```toml
[plugins.git]
name        = "git"
version     = "1.1.0"
description = "Git status integration for file panels"
author      = "contributor-handle"
languages   = ["en", "es"]
min_pairee  = "0.7.0"
```

`hooks` is an optional index field the client can display, but the packager never writes it (a manifest does not declare the events a plugin handles), and `tags` is not an index field at all.

### 3.2 Plugin `manifest.toml`

Located inside the plugin workspace directory and at `registry/plugins/<initial>/<author>/<name>/manifest.toml`. During packaging, the registry's copy is written from the author's manifest with `license` set and its `[files]` table **replaced** by the file list with SHA-256 hashes (the author's own folder and manifest are never modified). The manifest itself is not listed (a file cannot contain its own hash; it is covered by its `.minisig`), nor are hidden files or symbolic links; keys always use `/`. `name` and `author` must be `[A-Za-z0-9_-]`.

Pairee reads these keys of the manifest (`PluginManifest`, `src/plugin/loader.rs`): `name`, `version`, `description`, `author`, `license`, `min_pairee`, `requires_trust`, `default_language`, `languages`, `icon`, `screenshots`, `[keybindings]` (legacy), `[[commands]]`, `[settings_schema]` and `[permissions]`. Any other key (`homepage`, `tags`, `type`, `hooks`, ...) is accepted and **ignored**: it has no effect on loading, the index or the CLI output, and nothing is auto-detected from the plugin folder. A manifest may also nest all keys under a `[plugin]` table.

```toml
name         = "git"
version      = "1.1.0"
description  = "Git status integration for file panels"
author       = "contributor-handle"
license      = "MIT"
icon         = "icon.png"                       # 256x256 or 512x512, inside the plugin folder
screenshots  = ["screenshots/screenshot1.png"]  # at least one, 640x480 or larger

# Language integration support
default_language = "en"
languages    = ["en", "es"]

# Settings and options configuration schema
[settings_schema]
show_hidden = { type = "bool", default = false, description = "Show hidden VCS files" }
git_path    = { type = "string", default = "git", description = "Custom Git executable path" }
max_depth   = { type = "integer", default = 3, description = "Max directory recursion depth" }

# Minimum Pairee version required to run this plugin
min_pairee   = "0.7.0"

# Must the user opt-in to trusted mode for this plugin to work?
# Set to true if the plugin uses pairee.fs.spawn or needs os/io access
requires_trust = false

# Commands the plugin adds to the keymap and the palette
[[commands]]
id    = "run"
title = "Run"
[commands.keys]
default = "Ctrl+Alt+g"

# Programs it may spawn in Secure Mode (the user sees them before trusting it)
[permissions]
commands = ["git"]

# Set by the packaging tool in the registry's copy (replacing any [files]
# table of the author's manifest):
[files]
"main.lua" = "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
"utils.lua" = "c081d4a298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
"help/en.md" = "1a81d4a298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
"help/es.md" = "2a81d4a298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
"lang/en.toml" = "d081d4a298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
"lang/es.toml" = "f081d4a298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
"LICENSE" = "776289021cde9f6d1160160dd8603063af5f701d627e3b74c5f676a93b54aa09"
```

### 3.3 `sha256.sum`

Contains the lowercase hex SHA-256 hash of each file in the plugin folder:

```
e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855  main.lua
c081d4a298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855  utils.lua
1a81d4a298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855  help/en.md
2a81d4a298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855  help/es.md
d081d4a298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855  lang/en.toml
f081d4a298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855  lang/es.toml
```

## 4. `plugins.lock` — User-Side Lock File

Stored as `plugins.lock` in Pairee's config folder (`~/.config/FittyAr/Pairee/plugins.lock` on Linux, `~/Library/Application Support/FittyAr/Pairee/plugins.lock` on macOS, `%APPDATA%\FittyAr\Pairee\config\plugins.lock` on Windows). It is a TOML table `plugins` with one sub-table per installed plugin (`src/plugin/updater/lockfile.rs`, `types.rs`): the installed `version`, whether it is `pinned`, and a `files` table of relative path (`/` separated) to the lowercase SHA-256 of that file, `manifest.toml` included:

```toml
[plugins.git]
version = "1.1.0"
pinned = false

[plugins.git.files]
"main.lua" = "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
"manifest.toml" = "fa25d4a298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
"utils.lua" = "c081d4a298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
```

A missing file is an empty lock. A file that exists but cannot be parsed is an **error** (`pairee plugin verify` fails, installs and pins stop): it is never read as empty, and when a write has to replace an unreadable lock it is first moved to `plugins.lock.bak`. Plugins installed with "Install Local" from the Developer Tools are recorded the same way, with the hashes of the copied files.

## 5. CLI Commands Reference

All plugin management commands run through `pairee plugin <subcommand>`.

| Command | Description |
|---------|-------------|
| `pairee plugin list` | List the installed plugins with their version, `[PINNED]`, `[TRUSTED]`/`[UNTRUSTED]`, `[DISABLED]`, `[BLOCKED]` and, when the registry lists a newer version, `(Update available: vX)`. Works offline (the badges are then missing) |
| `pairee plugin search <query>` | Search the **remote** registry index (fetched and signature-checked) for plugins whose name or description contains the text, ignoring case. Author and tags are not searched; blocked plugins are left out |
| `pairee plugin info <name>` | Show the index metadata (version, author, description, `min_pairee`, languages, hooks if listed) and the file list of the signed manifest. A blocked plugin is an error. There is no version history, trust or keybinding summary |
| `pairee plugin install <name>` (alias `add`) | Download, verify the SHA-256 of each file and install the version the registry lists |
| `pairee plugin install <name>@<ver>` | Only accepted when `<ver>` is the version the registry lists (the registry keeps the latest version only); anything else is refused |
| `pairee plugin check-updates` | Contacts the registry and lists installed plugins with a newer registry version and blocked ones. A lower registry version is never offered |
| `pairee plugin update [<name>]` | Update one plugin, or every non-pinned one with a newer version (removing blocked ones). It runs the same install, so a plugin whose `min_pairee` or `--- @since` is too new for this Pairee is refused |
| `pairee plugin remove <name>` | Uninstall: the plugin folder, its `plugins.lock` entry, its data folder and its `config.toml` entries (trust, enabled flag, settings) |
| `pairee plugin pin <name>` / `unpin <name>` | Pin or unpin the installed version in `plugins.lock` (no version argument: the pin keeps the version installed now) |
| `pairee plugin verify` | Re-hash every installed file against `plugins.lock`, fail on blocked plugins, and report files in a plugin folder that the lock does not list and `.pairee` folders it does not know |

### 5.1 Badges in Search/List Results

`pairee plugin search` prints one block per match: `* <name> v<version> by <author>`, followed by `[Hook]` when the index entry lists hooks and one `[EN]`-style badge per language of the index entry, then the description on a second line. There are no plugin-type, colour or tag badges. `pairee plugin list` uses the status badges listed in section 5.

**Example CLI Search Output:**
```bash
$ pairee plugin search git
* git v1.1.0 by contributor-handle [EN] [ES]
  Description: Git status integration for file panels
```

## 6. Download & Verification Flow

```
pairee plugin install <name>        (TUI: Plugin Manager → Search → i)
  │
  ├─ 0. Read plugins.lock (a corrupt lock aborts here)
  ├─ 1. Fetch registry/blocklist.toml (+ .minisig)      ≤ 4 MiB
  │       blocked → abort; unreachable → abort (see "Blocklist" below)
  ├─ 2. Fetch registry/index.toml (+ .minisig)          ≤ 4 MiB
  │       signed: serial not below the last accepted one, not older than
  │       registry_max_age_days (6.1); resolve the latest version and author
  ├─ 3. Fetch plugins/<shard>/<author>/<name>/manifest.toml (+ .minisig)  ≤ 1 MiB
  │       its [files] table pins the SHA-256 of every file; its name and
  │       version must match the index entry (an older signed manifest is
  │       refused); it is installed from this signed text. Its (and the
  │       index's) min_pairee must not be above this Pairee
  ├─ 4. Validate every [files] key (no "..", absolute, drive, "\" or ":", no
  │       Windows device name, no trailing "." or space, no characters
  │       <>"|?*, no two keys equal ignoring case, no key that is both a file
  │       and a folder); at most 1000 files
  ├─ 5. Download each file into memory                  ≤ 16 MiB each, ≤ 64 MiB total
  │       compare its SHA-256 with [files] → any mismatch aborts, nothing written;
  │       main.lua's `--- @since` must not exceed this Pairee's plugin API
  ├─ 6. Stage: copy the current plugin folder to <name>.pairee.staging, write
  │       every file, remove the files the previous version listed in
  │       plugins.lock that this version no longer ships (a path that is the
  │       very file just written, e.g. a case-only rename on a
  │       case-insensitive file system, is kept), then swap the staging
  │       folder in with two renames. A failure or a crash before the swap
  │       leaves the working install untouched. Files you added to the
  │       folder yourself are kept
  └─ 7. Update plugins.lock (read again after the download so pins changed
          meanwhile are kept; atomic write; the pin flag is kept)
```

**Blocklist.** The blocklist is the kill switch, so it fails **closed**: if it cannot be fetched (network error, HTTP error) install, update, search, info, `check-updates` and `verify` fail instead of continuing without it (`list` only warns and shows no `[BLOCKED]` badges). A 404 for `blocklist.toml` is an error once the registry is expected to be signed (`registry_require_signature` with `REGISTRY_SIGNED`, or after this installation has verified a signed file with the configured key); only an unsigned registry may lack the file, which then means nothing is blocked. An invalid signature always fails. A blocked plugin that is already installed is removed by `pairee plugin update`.

Every limit is enforced while streaming: a response is refused as soon as it
grows past its limit (and up front when `Content-Length` already exceeds it).
The updater never prints: operations return a report that the CLI prints and
the TUI shows in a toast.

### 6.1 Registry signatures (minisign)

The SHA-256 values come from the registry itself, so they only protect
against corrupted downloads. Authenticity comes from **minisign signatures**
of the files that carry those hashes:

| Signed file | Signature | Trusted comment must contain |
|-------------|-----------|------------------------------|
| `registry/index.toml` | `registry/index.toml.minisig` | `file:index.toml serial:<N> timestamp:<unix>` |
| `registry/blocklist.toml` | `registry/blocklist.toml.minisig` | `file:blocklist.toml serial:<N> timestamp:<unix>` |
| `registry/plugins/<s>/<author>/<name>/manifest.toml` | same path + `.minisig` | `file:plugins/<s>/<author>/<name>/manifest.toml` |

**Pinned key, no trust on first use.** Pairee verifies them with the same
minisign code as its self-updater (`update::signature::verify_with_key`)
against the **Pairee release key embedded in the binary**
(`RWSF5Q18I/R4tADVZ5LQzgP2gRzPD/yzWj0p5kw13d6g4+Ycwbn27Fm6`, the key that
signs releases): the registry is published by the same maintainers, and one
key means one secret to protect and one verification helper. Nothing is
learned from the network: the very first signed file an installation sees
is checked against that key like every later one. Prehashed signatures
only; the trusted comment (covered by the global signature) must name the
file by its path inside `registry/`, so a signature cannot be replayed for
another file. A fork or a private registry can set
`registry_public_key = "<base64 key>"` under `[security]` in `config.toml`.

**Freshness (anti-rollback).** The trusted comment of `index.toml` and
`blocklist.toml` also carries `serial:<N>` (one more on every signing) and
`timestamp:<unix seconds>` (when it was signed). Pairee records the highest
serial it accepted for each file, with the key, in `registry_state.toml` in
the config folder (not in a plugin data folder, which plugins can write),
and refuses:

* a signed index or blocklist **without** `serial:` and `timestamp:`;
* one whose serial is **lower** than the recorded one (an old signed index
  replayed by a mirror or an attacker: rollback). The same serial again is
  a refetch and is accepted;
* one signed more than `registry_max_age_days` days ago (`[security]`,
  default **30**; `0` turns the age check off): a frozen registry or mirror
  that keeps serving an old index. The error names the setting.

Plugin manifests need no freshness: the signed index names the version each
manifest must carry, and an older signed manifest is refused against it.
An unsigned file (see below) has no freshness to check.

**Missing signatures.**

* A signature that is present but does not verify **always** fails the
  operation (also for the blocklist), whatever the settings.
* `registry_require_signature = true` under `[security]` (the default):
  the binary declares the official registry signed
  (`plugin::updater::trust::REGISTRY_SIGNED = true` since the release after
  0.11.0), so a missing signature is refused from the very first fetch. A
  build with it off (a fork or private registry that is not signed yet)
  refuses a missing signature only after the installation has verified a
  registry file signed with the configured key (recorded in
  `registry_state.toml`), so stripping the signatures does not downgrade a
  signed registry; before that it is accepted with an **"unsigned"
  warning** (CLI report line, TUI toast).
* `registry_require_signature = false` accepts unsigned files with the
  warning, always.

**How the registry is signed.** `cargo xtask sign-registry <registry-dir>`
(from a Pairee checkout) signs `index.toml` and `blocklist.toml` with
`file:<name> serial:<N> timestamp:<now>`, where `N` is one more than the
serial in their current `.minisig` (or `--serial N`, which must be higher),
and every `manifest.toml` under `plugins/` with `file:<path>`. It shells
out to `minisign`, reads the secret key like the release signing does (the
contents of `MINISIGN_SECRET_KEY`, written to a private temporary file, or a
key file with `--key`; its password from `MINISIGN_PASSWORD`, otherwise
minisign asks), and checks every signature with `minisign -V` against the
key in `src/update/signature.rs` before it finishes.

On GitHub this runs in the **Sign registry** workflow of the
`plugin-registry` branch. Its template lives on master at
`.github/registry/sign-index.yml` (it is not a workflow of master). To
install it:

```bash
git switch plugin-registry
mkdir -p .github/workflows
git show master:.github/registry/sign-index.yml > .github/workflows/sign-index.yml
git add .github/workflows/sign-index.yml
git commit -m "ci: sign the registry index with a serial and a timestamp"
git push origin plugin-registry
```

It needs the repository secrets `MINISIGN_SECRET_KEY` and, if the key has
one, `MINISIGN_PASSWORD` (the ones `release.yml` uses). On every push that
changes a `.toml` under `registry/`, and when started by hand, it checks out
the branch tip and master, runs `cargo xtask sign-registry`, and commits the
`.minisig` files with `GITHUB_TOKEN` (`[skip ci]`; pushes made with
`GITHUB_TOKEN` never start workflows, so it does not loop). Runs are
serialized, so serials never collide. Because every push gets signed, the
branch must only take reviewed pull requests; required reviewers on a
`registry-signing` environment (commented out in the template) can also gate
each run.

**Keeping the index fresh.** Clients refuse an index older than 30 days by
default, so the index must be re-signed at least that often even when no
plugin changes. GitHub runs `schedule` triggers (and `workflow_dispatch` by
name) only for workflows on the default branch, so the signing steps live in
a composite action on master, `.github/actions/sign-registry`, used by two
workflows:

* `sign-index.yml` on `plugin-registry`: on every push that changes a
  `.toml` under `registry/`;
* `refresh-registry.yml` on master: every Monday at 04:17 UTC and by hand
  (Actions → *Refresh registry signature* → *Run workflow*).

Both share the `sign-registry` concurrency group, so serials never collide.
The secret key reaches only the environment of the signing step (never a
command line or a log); `cargo xtask` writes it to a private temporary file.

By hand, with the offline release secret key:

```bash
cargo xtask sign-registry /path/to/plugin-registry/registry --key ~/pairee.key
cd /path/to/plugin-registry
git add -A -- 'registry/*.minisig'
git commit -m "registry: sign index, blocklist and manifests"
```

`minisign -S` writes `<file>.minisig` next to the file; the default
(prehashed) mode is the one Pairee accepts. Signing the index by hand with
plain `minisign` must keep the trusted comment format above, with a serial
higher than the published one.

**Strict mode** is on: `REGISTRY_SIGNED` is `true` in
`src/plugin/updater/trust.rs` (from the release after 0.11.0), so
`registry_require_signature = true` refuses unsigned registry files on every
installation, including fresh ones. A fork that publishes an unsigned
registry must build with it off or set `registry_require_signature = false`.

## 7. Versioning Rules

Plugins follow **Semantic Versioning 2.0.0** (`MAJOR.MINOR.PATCH`):

| Component | When to increment |
|-----------|-------------------|
| `MAJOR` | Breaking change to the plugin's publicly observable behavior |
| `MINOR` | New capabilities, backward-compatible |
| `PATCH` | Bug fixes, no behavioral change |

## 8. Community Plugin Submission Workflow

With `pairee developer` (CLI) or the Developer Tools tab, shown when `plugins_developer_mode = true` is set in `config.toml`:
1. The developer prepares their plugin directory locally (`~/.config/FittyAr/Pairee/plugins/my-plugin.pairee`).
2. Runs the publication checks (section 9) and packages the plugin, from inside its folder:
   ```bash
   pairee developer package
   ```
   This generates `sha256.sum` containing hashes of every file in the directory. Nothing is signed locally: the registry signs after the merge (section 10).
3. Runs the submit wizard (`pairee developer submit`, or **Submit Plugin** in the Developer Tools tab). It packages the plugin, asks for a commit description and commits the staged registry copy on the `plugin-registry` branch of the local registry clone (`<cache>/temp_registry`); no other branch is created. A clone that still holds packaged but unsubmitted work is kept as it is, offline or not, instead of being reset to the registry.
4. Optionally gives a GitHub personal access token (typed without echo in the CLI). There is no fork URL to enter: the fork is the token owner's. With a token the Rust engine:
   * reads the account's login from the token (`GET /user`) and forks `FittyAr/Pairee` into it (`POST /repos/FittyAr/Pairee/forks`);
   * waits until the fork exists (polls for up to a minute; forking is asynchronous);
   * force-pushes `plugin-registry` to `https://github.com/<login>/Pairee.git` (refspec `+refs/heads/plugin-registry:refs/heads/plugin-registry`, the token goes through the credentials callback, at most one attempt, and a ref the server rejects is an error);
   * opens a Pull Request from `<login>:plugin-registry` to the official `plugin-registry` branch.

   Without a token the wizard prints the manual commands (add your fork as a remote, push `plugin-registry`, open the PR).

## 9. Publication Checks

There is no standalone validation script. `pairee developer package`, `pairee developer submit` and the TUI Package / Submit options run these checks and stop at the first failure (`plugin::developer_tool::validate_for_publish`, then the name check in `registry_plugin_dir`). In this order:

1. `manifest.toml` exists in the current directory and parses as a `PluginManifest`.
2. **Icon:** `icon` is set; the file is among the files that would be published (a regular, non-hidden file inside the plugin folder: `../x.png`, absolute paths, links and hidden files are refused) and exists; it is a readable image of exactly 256x256 or 512x512 pixels.
3. **Screenshots:** `screenshots` lists at least one file; each is published the same way, a readable image of at least 640x480 pixels.
4. **Entry point and files:** `main.lua` exists; every file name is accepted by the installer (no Windows device name, trailing dot or space, characters `<>"|?*`, names equal ignoring case); at most 1000 files, each at most 16 MiB, at most 64 MiB in total (the generated manifest and `sha256.sum` are not counted).
5. `name` and `author` only use `[A-Za-z0-9_-]` (they become the registry path `plugins/<shard>/<author>/<name>/`). This runs **before** anything is fetched, written or deleted.

The packager then resolves the license, clones or refreshes the registry, copies the plugin files into `registry/plugins/<shard>/<author>/<name>/`, writes `sha256.sum`, the manifest (license set, `[files]` replaced by the checksums) and, when the plugin has no license file, a generated MIT `LICENSE` there, and updates `registry/index.toml`. The author's own folder is not modified at any step.

Lua syntax, translation coverage, key alignment and encoding are **not** checked at packaging time. `pairee developer lint` covers part of it (manifest and `default_language`, `main.lua` present, unsafe calls in untrusted plugins, suggested keys per preset; it leaves the keymap's plugin commands as they were); the rest is up to the reviewer of the pull request.

## 10. CI on the `plugin-registry` Branch

**Target.** The branch signs through one workflow, `sign-index.yml`, whose template lives on master at `.github/registry/sign-index.yml` (installation steps in 6.1). On every push that changes a `.toml` under `registry/`, and when started by hand or by the weekly refresh workflow on master, it runs `cargo xtask sign-registry`: `index.toml` and `blocklist.toml` are signed with `file:<name> serial:<N> timestamp:<now>` (the serial is one more than the published one, runs are serialized), every plugin `manifest.toml` with `file:<path>`, each signature is verified against the key embedded in Pairee, and the `.minisig` files are committed with `GITHUB_TOKEN` (`[skip ci]`). Signing can run in the `registry-signing` environment, so required reviewers can approve each run.

**Current state of the branch.** `sign-index.yml` is installed on `plugin-registry` (it replaced the older `sign-registry.yml`, which signed without `serial:` and `timestamp:`) and calls the shared action on master; `refresh-registry.yml` re-signs weekly. The first serial-signed index was published on 2026-10-15.

No workflow validates pull requests or regenerates `index.toml`: the index is written by the packager (section 9) and reviewed in the pull request. Because anything merged is signed with the release key, keep the branch protected (pull requests with review).
